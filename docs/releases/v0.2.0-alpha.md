# qradar-soar-mcp v0.2.0 (alpha)

> **Release status: pending.** This is a draft for a GitHub **pre-release** of the
> source code. No `v0.2.0` tag or release exists yet, and the release gate has not
> passed (see [Distribution restrictions](#9-distribution-restrictions)). This
> release makes **no production-readiness claim**.

The links below point at the `v0.2.0` tag and resolve once that tag exists.

## 1. Release summary

`qradar-soar-mcp` is a security-first [MCP](https://modelcontextprotocol.io) server
that connects Claude to IBM QRadar SOAR for incident investigation and tightly
controlled changes. `v0.2.0` is the **Phase-1 milestone**: Phase 1 is complete in code,
with deferrals that are documented. It also includes early Phase-2 discovery tools.
**Phase 2 is incomplete**, and `v0.3.0` is not ready.

Everything except reading is off by default. Live API verification is limited to one
appliance version, **IBM QRadar SOAR `51.0.9.0.20848`**.

## 3. Security model and safe defaults

- **Deny by default.** Every capability flag is off. Absent, empty or unparseable values
  resolve to the safe side, and `.env.example` enables nothing.
- **Tiers.** Tier 0 (reads) is always on. Tiers 1–2 each need their own flag. Tier 3
  needs a flag, a valid action policy and out-of-band approval, and is unavailable in
  this release. Tier 4 has **no tools**. Tier 5 (bulk, delete, script writes, AppHost
  changes) has no flag and no tool, by design.
- **One enforcement pipeline** for every tool, pinned by AST and permission-matrix
  tests: flag, policy, tier, transport, kill switch, circuit breaker, one-object cap,
  approval, audit, hourly cap, the SOAR call, audit, redaction.
- **Blast-radius limits.** One object per call, hourly caps on Tier 2 and Tier 3, a
  circuit breaker and a kill-switch file.
- **Hash-chained audit log.** A mutation is refused if its audit record cannot be
  written.
- **Lab-only switches.** Turning off TLS verification or a confirmation switch, or using
  `in_band`/`disabled` approval with actions or a Tier-4 flag enabled, refuses to start
  without `SOAR_LAB_MODE=true`.
- **Transport.** stdio is the supported transport. Streamable HTTP needs a bearer token,
  binding all interfaces needs an explicit acknowledgement, and Tier ≥ 3 is always
  denied over HTTP.
- **Untrusted content.** Incident text and SOAR configuration (scripts, workflow and
  playbook XML) are treated as data. Scripts are never run, and no request that writes a
  script exists.
- **Approvals.** The approval broker is implemented and tested offline, but it is **not
  reachable through a supported action tool** in this release.

Details: [threat model](https://github.com/lancyandrade/qradar-soar-mcp/blob/v0.2.0/docs/threat-model.md)
and [SECURITY.md](https://github.com/lancyandrade/qradar-soar-mcp/blob/v0.2.0/SECURITY.md).

## 5. Installation from the GitHub source tag

This release is source code only. Install it from the tag:

```bash
git clone --branch v0.2.0 --depth 1 https://github.com/lancyandrade/qradar-soar-mcp
cd qradar-soar-mcp
uv sync --locked
uv run qradar-soar-mcp --version
```

You can also download the "Source code" archive GitHub generates for the tag, extract
it and run `uv sync --locked` in the extracted directory. **There is no PyPI package**,
and no wheel or sdist is attached to this release.

To run the offline test suite: `uv sync --locked --extra dev`, then `uv run pytest`.

## 6. Configuration and safe startup

1. **Create a read-only API key** in SOAR (Administrator Settings → API Keys). Start
   with read-only tools.
2. **Copy the example configuration.** `cp .env.example .env` and fill in the
   connection values. The server reads only its process environment, never a `.env`
   file, so export the variables or set them in your MCP client configuration. The
   example leaves every capability flag `false`.
3. **Keep TLS verification on.** For a private CA, set `SOAR_CA_BUNDLE` to a PEM bundle
   instead of turning verification off.
4. **Set absolute paths** for `SOAR_AUDIT_LOG_PATH` and `SOAR_KILL_SWITCH_FILE`.
5. **Check before serving.** `uv run qradar-soar-mcp --check` prints a JSON report with
   no secrets and sends one read-only search. Exit code 0 means reachable, 1 not
   configured or unreachable, 2 configuration refused.
6. **Enable writes one flag at a time**, and only after reading the threat model. Try
   Tier 1–2 flags first against a lab or disposable organisation, because those write
   contracts were not exercised live.
7. **Run two instances with two keys**: a read-only one for routine use and a separate,
   narrowly scoped one for writes. See the README section
   [Recommended deployment](https://github.com/lancyandrade/qradar-soar-mcp/blob/v0.2.0/README.md#recommended-deployment-two-instances-two-keys).
8. **Never set `SOAR_LAB_MODE=true` outside a lab.**

Every variable is described in the README
[configuration reference](https://github.com/lancyandrade/qradar-soar-mcp/blob/v0.2.0/README.md#configuration-reference).

## 7. Known limitations

- **Phase 2 is incomplete.** P2-06 (policy scaffold CLI) and P2-07 (historical-response
  analysis) are not started; P2-00, P2-01 and P2-03 are partial.
- **Manual-action invocation always returns `DENY_UNSUPPORTED`.** SOAR's invocation
  contract is unverified, so nothing is sent and Tier 3 cannot be used.
- **The approval broker is implemented but not reachable through a supported action
  tool.**
- **No Tier-4 playbook mutation tools.** Nothing creates, changes, exports, imports,
  deploys or enables a playbook, workflow or script.
- **Attachment hash and text extraction are deferred.** Attachment contents are never
  fetched.
- **Tier-1/2 mutations are primarily offline-contract-tested, not live-validated.** Only
  the task-status change was exercised live, and it has no protection against a
  concurrent edit.
- **Live API verification is limited to IBM QRadar SOAR `51.0.9.0.20848`.**
- The `export` catalog source always fails. `soar_describe_incident_fields` still
  derives `close_required` from an unverified reading.
- The server cannot check its API key's SOAR permissions. Successful reads are not
  audited, and Tier-1 writes have no hourly cap.

## 9. Distribution restrictions

- The release is a git tag and a **GitHub pre-release of the source code only**.
- The only downloads are the source archives GitHub generates from the tag.
- **No manually built wheel, sdist or other binary is attached.**
- **Nothing is published to PyPI.**
- Build artefacts wait for REL-04 (artefacts built only by a tag-triggered CI workflow
  from a clean checkout, with checksums). REL-06 (the sdist allow-list) is complete;
  REL-04 is open.
- The release-readiness verdict is **NO-GO** until the lab gate is evidenced. The owner
  accepted the P1-15 attachment-processing deferral and the D4 invocation limitation as
  alpha scope; neither feature is implemented.
